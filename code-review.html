Relatório de Code Review Full-Stack — Front-end & Back-end (GearRent)

Auditoria arquitetural, funcional e didática completa da pilha Web: Front-end (Vanilla JS, HTML5, CSS3 e Axios) e Back-end (Java 17, Spring Boot 4.1.1, Spring Security JWT, Spring Data JPA/Hibernate e PostgreSQL).

Front-end: HTML5, CSS3, Vanilla JS + Axios Back-end: Java 17, Spring Boot 4.1.1, PostgreSQL Padrão: DDD Simplificado + Multi-Tenant (locadoraId via JWT) Contrato de Erro: @RestControllerAdvice → ApiErroResposta(mensagens) Nível Alvo: Desenvolvedor Iniciante
Visão Geral da Saúde do Projeto: O projeto GearRent demonstra uma maturidade muito acima da média para um desenvolvedor iniciante. Há decisões arquiteturais dignas de elogio: uso de Java Records como DTOs em todos os Controllers (sem vazar entidades JPA diretamente), Lock Pessimista (PESSIMISTIC_WRITE) ao reservar equipamentos e atualizar locações, modelo de domínio rico na entidade Locacao, tratamento global padronizado em GlobalExceptionHandler com ApiErroResposta e prevenção consistente contra XSS no Front-end utilizando document.createElement e textContent.

🚨 Principais Riscos de Segurança & Multi-Tenancy

Credenciais reais do PostgreSQL (Render) e senha de aplicativo Gmail expostas no application.properties; conflito de URLs da API hardcoded no Front-end; constraint global @Column(unique = true) no CPF de Usuario quebrando o isolamento por locadoraId; e anotação @PreAuthorize colocada por engano em um DTO Record.

⚙️ Principais Bugs & Furos de Fluxo

Condição de corrida na geração do codigoSequencial de Equipamentos; vazamento de clientes excluídos no dropdown de filtros; ausência de @Enumerated(EnumType.STRING) em dois enums JPA; quebra de contrato no PUT /api/usuarios/me (ignora o CPF enviado pelo Front); e parâmetro ?clienteId ignorado ao abrir a tela de Locações.

🎓 Adequação ao Nível Iniciante

Foram detectados pontos de complexidade desnecessária que dificultam a manutenção: um roteador SPA manual em api.js usando DOMParser e injeção dinâmica de tags <script>, filtragem tardia em memória na Auditoria após findTop200, duplicação de funções utilitárias em 5 arquivos JS e um arquivo CSS único com 6.358 linhas.

function tokenClaims() {

      .replace(/-/g, '+')
      .replace(/_/g, '/');

    return {};

05. Anotação @PreAuthorize Inócua em DTO Record e Endpoint GET /api/usuarios sem Restrição de Papel

application/DTO/UsuarioAtualizacaoRequest.java:10 & presentation/UsuarioController.java:53

Explicação: No arquivo UsuarioAtualizacaoRequest.java (linha 10), foi colocada a anotação @PreAuthorize("hasRole('ADMIN') or #id == principal.id()") em cima da declaração do record DTO. O Spring Security AOP ignora completamente anotações @PreAuthorize em DTOs (elas só funcionam em métodos de Beans gerenciados pelo Spring, como Controllers ou Services). Além disso, em UsuarioController.java (linha 53), o endpoint GET /api/usuarios (que lista todos os operadores, e-mails, CPFs e status da base) não possui @PreAuthorize("hasRole('ADMIN')"), permitindo que qualquer operador comum liste os dados cadastrais dos demais operadores.

❌ Como está (Código Atual)
// 1) Em UsuarioAtualizacaoRequest.java (anotação morta em um Record DTO):
@PreAuthorize("hasRole('ADMIN') or #id == principal.id()")
public record UsuarioAtualizacaoRequest(
        @NotBlank(message = "O nome é obrigatório.") String nome,
        // ...
) {}

// 2) Em UsuarioController.java (linha 52 — sem @PreAuthorize):
@GetMapping
public ResponseEntity<List<UsuarioConsultaResponse>> listar(
        @AuthenticationPrincipal UsuarioAutenticado usuario,
        @RequestParam(required = false, defaultValue = "") String nome) {
    return ResponseEntity.ok(usuarioService.listarUsuariosDaMinhaBase(usuario.locadoraId(), nome));
}
✅ Como deveria ser (Código Corrigido)
// 1) Em UsuarioAtualizacaoRequest.java (remova @PreAuthorize do DTO):
public record UsuarioAtualizacaoRequest(
        @NotBlank(message = "O nome é obrigatório.") String nome,
        // ...
) {}

// 2) Em UsuarioController.java (proteja a listagem de operadores da base):
@GetMapping
@PreAuthorize("hasRole('ADMIN')")
public ResponseEntity<List<UsuarioConsultaResponse>> listar(
        @AuthenticationPrincipal UsuarioAutenticado usuario,
        @RequestParam(required = false, defaultValue = "") String nome) {
    return ResponseEntity.ok(usuarioService.listarUsuariosDaMinhaBase(usuario.locadoraId(), nome));
}

06. Condição de Corrida (Race Condition) na Geração do codigoSequencial de Equipamento

application/service/EquipamentoService.java:62-66 & domain/repository/LocadoraRepository.java:16-21

Explicação: Para gerar a numeração sequencial por locadora (1, 2, 3...), ClienteService utiliza corretamente a query atômica locadoraRepository.proximoCodigoCliente(locadoraId) (UPDATE locadora SET ultimo_codigo_cliente = ultimo_codigo_cliente + 1 ... RETURNING). Porém, EquipamentoService.cadastrar calcula int codigo = equipamentoRepository.buscarUltimoCodigo(locadoraId) + 1 (via SELECT MAX(codigoSequencial)). Se dois operadores da mesma locadora cadastrarem um equipamento ao mesmo tempo, ambos lerão o mesmo MAX antes do commit e um deles falhará! O mais curioso é que o método atômico locadoraRepository.proximoCodigoEquipamento(locadoraId) já foi criado em LocadoraRepository.java (linha 21), mas nunca foi chamado.

❌ Como está (Código Atual em EquipamentoService.java)
// SELECT MAX() + 1 está sujeito a condição de corrida em requisições simultâneas:
int codigo = equipamentoRepository.buscarUltimoCodigo(locadoraId) + 1;
if (equipamentoRepository.existsByLocadoraIdAndCodigoSequencial(locadoraId, codigo)) {
    throw new ConflitoException(
            "Outro equipamento acabou de ser cadastrado. Tente salvar novamente.");
}
equipamento.setCodigoSequencial(codigo);
✅ Como deveria ser (Código Corrigido)
// Reutilize o UPDATE ... RETURNING atômico que já existe no LocadoraRepository:
Long proximoCodigo = locadoraRepository.proximoCodigoEquipamento(locadoraId);
equipamento.setCodigoSequencial(proximoCodigo.intValue());

08. Ausência de @Enumerated(EnumType.STRING) em Entidades JPA e Uso de double para Valores Monetários

domain/entities/Equipamento.java:41 & domain/entities/Locacao.java:49-52

Explicação: Na entidade Equipamento (linha 41), o atributo private StatusEquipamento status; não possui a anotação @Enumerated(EnumType.STRING). O mesmo ocorre em Locacao (linha 49) no campo private TipoPagamento tipoPagamento;. Por padrão, o JPA grava enums sem essa anotação como números inteiros (ORDINAL: 0, 1, 2...) no banco de dados. Se alguém alterar a ordem das constantes no enum Java, todos os registros do banco ficam com o status ou tipo de pagamento trocados! Além disso, Locacao armazena valorDesconto, valorMultaPorAtraso e valorFinalCobrado como double primitivo em vez de BigDecimal, o que pode gerar imprecisões de ponto flutuante (ex: 19.990000000000002) e obriga conversões constantes ao usar a CalculadoraLocacao.

❌ Como está (Código Atual)
// Em Equipamento.java:
@Enumerated(EnumType.STRING)
private CategoriaEquipamento categoria;
private StatusEquipamento status; // ❌ Grava 0, 1, 2, 3 no banco (EnumType.ORDINAL)

// Em Locacao.java:
@Enumerated(EnumType.STRING)
private StatusLocacao status;
private TipoPagamento tipoPagamento; // ❌ Grava ordinal no banco
private double valorDesconto;        // ❌ double para dinheiro
private double valorMultaPorAtraso;
private double valorFinalCobrado;
✅ Como deveria ser (Código Corrigido)
// Em Equipamento.java:
@Enumerated(EnumType.STRING)
private CategoriaEquipamento categoria;

@Enumerated(EnumType.STRING)
private StatusEquipamento status;

// Em Locacao.java:
@Enumerated(EnumType.STRING)
private StatusLocacao status;

@Enumerated(EnumType.STRING)
private TipoPagamento tipoPagamento;

@Column(precision = 12, scale = 2)
private BigDecimal valorDesconto = BigDecimal.ZERO;

@Column(precision = 12, scale = 2)
private BigDecimal valorMultaPorAtraso = BigDecimal.ZERO;

@Column(precision = 12, scale = 2)
private BigDecimal valorFinalCobrado = BigDecimal.ZERO;

09. Quebra de Contrato em PUT /api/usuarios/me e Validação de CPF/CNPJ Apenas por Quantidade de Dígitos

application/DTO/PerfilAtualizacaoRequest.java:7-16 & ClienteCadastroRequest.java:17-19

Explicação: Na tela de Configurações (configuracoes.js:574), o formulário "Meu Perfil" possui um campo editável de CPF e envia { nome, sobrenome, email, cpf } para PUT /api/usuarios/me. No entanto, o DTO PerfilAtualizacaoRequest no Back-end não possui o campo cpf (e o método UsuarioService.atualizarPerfil não atualiza o CPF). // Em PerfilAtualizacaoRequest.java (ignora o CPF enviado pelo Front-end):

        @NotBlank(message = "Informe o seu e-mail.") @Email String email) {
}

// Em UsuarioService.java:
public PerfilConsultaResponse atualizarPerfil(Long locadoraId, Long idUsuario, PerfilAtualizacaoRequest request) {

🚀 Dicas de Aprendizado e Próximos Passos

1. Parabéns pelo Isolamento Multi-Tenant e Lock Pessimista!

O uso de @AuthenticationPrincipal UsuarioAutenticado extraindo o locadoraId diretamente do token JWT (nunca do corpo da requisição) e o uso de @Lock(LockModeType.PESSIMISTIC_WRITE) em EquipamentoRepository.buscarParaLocacao mostram excelente domínio de segurança e concorrência no Spring Boot.

2. Excelente Prevenção contra XSS e Uso de Java Records

No Front-end, criar elementos com document.createElement e popular textos via textContent protege a aplicação contra ataques de Cross-Site Scripting (XSS). No Back-end, o uso de record para todos os DTOs de entrada e saída mantém os Controllers limpos e desacoplados das entidades JPA.

3. Nunca Versione Senhas Reais no application.properties

Troque imediatamente a senha do banco PostgreSQL no painel do Render e revogue a senha de aplicativo do Gmail exposta no código. Utilize variáveis de ambiente (${DB_PASSWORD}, ${MAIL_PASSWORD}, ${JWT_SECRET}) sem valores reais de produção como fallback.

4. Use Sempre @Enumerated(EnumType.STRING) e BigDecimal

No JPA/Hibernate, todo atributo do tipo enum deve ter @Enumerated(EnumType.STRING) para gravar o nome legível no PostgreSQL e evitar corrupção caso a ordem do enum mude. Para valores financeiros em entidades (como descontos, diárias e multas), prefira sempre BigDecimal em vez de double.

5. Mantenha o Contrato Front-end ↔ Back-end Alinhado

Sempre confira o arquivo GlobalExceptionHandler.java e os Records de Request/Response ao construir formulários no Front-end. Use erro.response?.data?.mensagens?.[0] de forma padronizada em um único utilitário global em js/api.js e garanta que todo campo enviado pelo Axios exista no DTO correspondente do Spring Boot.

6. Simplifique o Front-end (MPA Puro + DRY)

Para um projeto iniciante em Vanilla JS, remova o roteador SPA com DOMParser de api.js e deixe os links HTML navegarem normalmente, mantendo apenas a restauração rápida da sidebar via sessionStorage. Isso elimina bugs de eventos duplicados e deixa o fluxo fácil de depurar pelo DevTools (F12).
